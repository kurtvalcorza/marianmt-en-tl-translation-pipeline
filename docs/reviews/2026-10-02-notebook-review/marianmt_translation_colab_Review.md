## Executive assessment

This is one of the strongest guided notebooks in the fleet. The default path is careful and honest: the pickle
checkpoint is digest-verified before it is opened and loaded with `weights_only=True`; the corpus is a real,
digest-pinned Tatoeba zip, filtered, de-duplicated on the English side and split without source leakage; the
pretrained model is scored beside a copy-source baseline on the same 300 sentences; adaptation is bounded, its
selection uses validation only, and the test split is touched once; corpus scores are paired with sentence-level
changes, negative results are kept, surface flags are calibrated on the human references, and the controlled
activity reports cues instead of a quality score. The guided layer (driving question, How to use, Input → Model →
Output, roadmap, five checkpoints with sample answers, an inert Predict → Change → Run activity, troubleshooting,
glossary, conclusion scaffold) is complete. A direct CPU execution in this review reproduced the recorded CPU
pre-flight numbers exactly.

Two problems stop it being ready, and both are the same defect seen from two learner journeys. **`pipe.adapt` never
returns to the base weights, and the notebook's re-run instructions keep using the same `pipe`.** After a default run,
the documented experiment "set `NUM_BEAMS = 1` … re-run from its cell" prints an adapted model as the "pretrained"
column and as the Section 7 frozen score (58.75 chrF; a fresh base scores 56.75 greedy), labels the adapted model
"frozen model" at epoch 0 (validation 61.50; true 58.55), and then stops at the Section 9 assertion, which tells the
learner that "the pinned sample run no longer reproduces the recorded gain" (P2). The BYOD instruction "re-run from
that cell" has the same effect: the BYOD "pretrained" baseline is a Tatoeba-adapted model, and the BYOD adapter
records `best_epoch 0` ("pretrained kept") while carrying earlier training (P3). Eight Minor findings cover the BYOD
size contract, the Section 9 assertion under experiments, the missing Colab record for this blob, Infrastructure
collapse that Colab does not honour, contradictory external-access text, an unstated CPU/GPU difference in the
adapted numbers, BYOD "new sentences" that are already-scored test rows, and an undocumented environment variable.

No finding here says the recorded default-path numbers are wrong.

## 2. Separate judgments

**Technical correctness.** Strong: identity carried twice and asserted, digest checks before deserialisation,
`weights_only=True`, transactional `adapt` on failure, digest-bound adapter with tensor allow-list, reload parity
asserted, every export written by the run that produced it. The defect is re-entrancy: `adapt()` (`pipeline.py:473`)
starts from whatever weights `pipe` holds, and Sections 6–9 always use that `pipe`, so any documented re-run after the
first adaptation measures, labels and exports a stacked model (MMT-M1, MMT-M2). The BYOD size bounds stated in the
contract are not the bounds the code enforces (MMT-m1).

**Promise fulfilment.** Every default-path promise is delivered and evidenced by the exact-blob Kaggle run and this
review's CPU run. The optional-experiment promise ("change one knob, re-run from its cell, and compare with the
recorded run") is not: the comparison is against a mislabelled baseline and can end in a regression assertion
(MMT-M1, MMT-m2). The BYOD promise ("the same … baselines, fine-tuning, held-out evaluation … as the Tatoeba sample")
is not delivered when BYOD follows the default run as instructed (MMT-M2).

**Learner experience.** Excellent on the default path: every stage states its question, a prediction is asked
before results, What-to-notice notes avoid hard-coded numbers, and the conclusion scaffold forces evidence-bounded
claims. The Infrastructure label is present, but the collapse uses a metadata key Colab does not read (MMT-m4), and
two statements about external access contradict each other (MMT-m5).

**Spec conformance.** Unresolved applicable `MUST`s on the documented re-run paths: SRC2, OUT8, ART8, UX7 (MMT-M1);
DAT13, DAT14, OUT8, ART8 (MMT-M2); DAT12, DAT19, VAL1, VAL6 (MMT-m1); ENV8 (MMT-m6); REL1/REL11 cannot be confirmed
for the supported Colab runtime (MMT-m3). `SHOULD` deviations: GDL10, GDL11, UX10, EXE5, SRC3, INF2.

## 5. Findings

### Major

#### MMT-M1 — The documented experiments re-run on the already-adapted model and mislabel it as "pretrained" and "frozen"

- **Cell/section:** "How to use" step 2 (cell 1), Optional experiments (cell 46), Sections 6b/7/8/9 (cells 24, 27, 30,
  33); package `pipeline.py:473` `adapt()`; template `tools/notebook_template.py:161, 981`.
- **Observed issue:** `adapt()` trains the parameters `pipe` currently holds; nothing restores the base. The notebook
  tells learners to "change one knob and re-run from that cell downwards" and lists `NUM_BEAMS = 1`, `EPOCHS`,
  `TRAINABLE_DECODER_LAYERS = 6` as experiments. After a default run, `NUM_BEAMS = 1` re-run from Section 6a gives:
  a 6b "pretrained" column and a Section 7 `frozen_model_test` that are the adapted model (chrF 58.75; the evaluator's
  own record says `adapted: true`; a fresh base scores 56.75 greedy); an epoch 0 labelled `frozen model` at
  validation chrF 61.50 (true 58.55); a second adaptation stacked on the first; and a Section 9 comparison where
  "adapted" (58.43) is below "frozen" (58.75), ending in `AssertionError: the pinned sample run no longer reproduces
  the recorded gain`. The `EPOCHS` and `TRAINABLE_DECODER_LAYERS` experiments re-run only Section 8 onward, so their
  epoch 0 is likewise the adapted model (source inspection).
- **Consequence:** the notebook's own optional experiments teach a wrong conclusion ("greedy decoding makes the model
  better than beam search, and adaptation then hurts"), blur the inference/adaptation distinction that objective 2
  teaches, and end with a message telling the learner to report a regression.
- **Evidence:** direct execution, local CPU (P2); source inspection of `adapt()`.
- **Recommended correction:** make `adapt()` start from the verified base every call (store the base `state_dict` of
  the adaptable decoder blocks at load and restore it at entry, or keep an untouched base and adapt a copy), and make
  Sections 6b/7 use a base pipeline explicitly (e.g. `base = MarianMTTranslationPipeline.from_pretrained(...)` kept
  separate from `pipe`), or assert `pipe.adapter is None` at the top of Section 6b with a message naming the cell to
  re-run. Fix it in the package and regenerate; add a regression test: two consecutive `adapt` calls give identical
  epoch-0 validation metrics.
- **Acceptance check:** after a default run, setting `NUM_BEAMS = 1` and re-running from Section 6a prints a Section 7
  frozen chrF equal to a fresh base's greedy score on the same split (56.75 on CPU) with `adapted: false`, an epoch 0
  equal to the fresh base's validation score, and no AssertionError from a contaminated baseline.
- **Spec:** GDL10, UX5, UX7, SRC2, EVAL10, OUT8, ART8.

#### MMT-M2 — BYOD "re-run from that cell" compares the user's data against a Tatoeba-adapted "pretrained" model

- **Cell/section:** opening BYOD paragraph (cell 0), BYOD steps (cell 46), Sections 4–12 (cells 16–43); template
  `tools/notebook_template.py:59`.
- **Observed issue:** the BYOD instructions run after the default path and reuse the same `pipe`. In P3 the BYOD
  "pretrained" test score was 52.41 chrF with `adapted: true` (a fresh base: 51.80), epoch 0 "frozen model" scored
  60.07 on BYOD validation (fresh base: 58.92), and selection kept epoch 0, so the notebook reported "adaptation did
  not raise held-out chrF on your data" against a model that had already been fine-tuned on Tatoeba. The exported
  adapter's manifest records `best_epoch 0`, 260 training pairs and the BYOD data source, while its tensors are the
  earlier in-memory training; reload parity (8/8) passes because only the same two blocks differ from the base, so
  nothing flags it.
- **Consequence:** the learner's central BYOD comparison (pretrained vs adapted on their own references) is wrong, and
  the exported artifact misdescribes how it was produced — the user cannot reconstruct it from its manifest.
- **Evidence:** direct execution, local CPU, `BYOD_PATH` (P3; that run followed P2, so it started from two earlier
  adaptations — with only the default run before it, the defect is the same, by the code path in M1).
- **Recommended correction:** the base reset of MMT-M1, plus a guard at the top of Section 4 (or 6b) that rebuilds
  `pipe` from the verified snapshot when `pipe.adapter is not None`, and an adapter-manifest field recording the
  starting weights (base digest only, or base + prior adapter digest).
- **Acceptance check:** after a default run, a BYOD re-run with the P3 400-row CSV prints a Section 7 pretrained chrF
  equal to a fresh base on that test split (51.80 on CPU) with `adapted: false`; the adapter manifest's history starts
  from that base.
- **Spec:** DAT13, DAT14, EVAL10, OUT8, ART8, ART4.

### Minor

#### MMT-m1 — The BYOD size contract is not the one the code enforces, and large data fails after the model loads

- **Cell/section:** Prerequisites "Data contract" (cell 4), BYOD steps (cell 46); `samples.py` `split_dataset`,
  `pipeline.py` `MAX_EVAL_RECORDS = 2_000`.
- **Observed issue:** the contract says "a dataset needs 8..20,000 records". 8–11 unique sources fail at the split
  (`split leaves 5 training records; at least 8 are required`); above ~10,000 records the 20 % test split exceeds the
  unstated `MAX_EVAL_RECORDS = 2,000` and `pipe.evaluate` raises in Section 7, after the 296 MB model is loaded and the
  data was "validated"; above ~13,300 the validation split fails inside `adapt`.
- **Consequence:** valid-looking data is rejected late, with a message about record counts rather than the split or
  evaluation ceiling.
- **Evidence:** direct execution of the carried module code (P4).
- **Recommended correction:** state the effective bounds (at least 12 unique sources; at most the size whose test and
  validation splits fit `MAX_EVAL_RECORDS`) in the Prerequisites, and check the split sizes against
  `MAX_EVAL_RECORDS` in Section 4 with a message naming the ceiling and the fix (fewer records or a smaller
  fraction).
- **Acceptance check:** a 12,000-record BYOD file is refused in Section 4 with a message naming `MAX_EVAL_RECORDS`;

- **Spec:** DAT12, DAT19, VAL1, VAL6.
